# The full work

> Confidence note: this is Path A from the upstream market research file `Skills-Results/work-package-manager/market-research/2026-06-24_18-41_work-package-manager-rerun-scenarios-market-research-result.md`. No field validation has been retired since that research in this run.

<a id="l3-value"></a>
## 0. Headline value statement
**WPM turns fragile agent setup handoffs into verified local runs.**

For authors who repeatedly ship agent profiles, MCP setups, skills, and toolchains to people whose environments they cannot inspect, WPM is a work-package builder that lets the recipient's own agent preview, execute, verify, repair, update, and uninstall the setup with receipts. Unlike README files, native single-runtime distribution, or component registries, it packages the work needed to make the capability true in the recipient's environment.

## 1. Target segment
**Cross-runtime setup authors** are people or teams who repeatedly hand off an agent setup to someone else and then absorb the install/support cost when the recipient's environment differs.

Causal criteria:
- They have shipped the same or similar setup at least 3 times.
- The setup includes multiple moving parts: profile/config, skills, MCP servers, scripts, local files, credentials, target-agent surfaces, or verification.
- The recipient runs it in an environment the author cannot inspect.
- A failed install creates author support work, reputational risk, or delayed delivery.
- At least one target is outside a single native runtime path, or the author wants evidence beyond "follow these docs."

Dominant success criteria:

| Criterion | Concrete level | Cost dimension reduced | Priority reason |
|---|---|---|---|
| Install completes in unknown environments | 4/5 pilot installs complete without author remote control; each ends with observable verification | Probability of outcome, time, negative emotion | A failed install creates support work and trust damage |
| Author support thread shrinks | Median author support time per recipient install falls below 15 minutes | Time, effort, cognitive load | The author is buying back repeated support time |
| Recipient keeps local control | No secrets leave the recipient environment; all dangerous steps have plan preview and approval; receipt states what changed | Negative emotion, privacy/control, trust | Secret handoff or opaque execution blocks adoption |
| Lifecycle is re-enterable | At least one update, repair, or uninstall can run from the prior receipt without rediscovering local decisions | Reliability, future support time | The first install is not the whole Job; maintenance creates the recurring value |

Priority order: **reliability-first + no-stress-first + control-first**. Done-for-me matters, but only if local control is preserved.

Lead mechanics:
- Fix Critical Chain breaks before the setup reaches value.
- Reduce role-to-role hand-offs between author, recipient, and recipient's agent.
- Kill cycles in the install/support chain.
- Take parts of the setup Job off the author.
- Remove negative emotions around "what did this agent just change?"
- Raise probability of outcome through plan preview, verification, and receipts.

<a id="l3-segment"></a>
## 2. The job, in the customer's own words
**Core Job 1.** When I have a working agent/profile/MCP/toolchain setup and need other people to run it in environments I cannot inspect, I want to package the setup as executable work with checks, approvals, and receipts, with success criteria that the recipient's own agent can install it, verify it, pause safely, and report what changed, in order to distribute a working capability without turning every install into a support thread.

**Core Job 2.** When the setup changes or drifts later, I want the recipient's agent to update, repair, or remove it from the recorded state, with success criteria that local decisions and secrets are preserved, in order to keep the capability working without re-supporting the whole install.

**Big Job.** Distribute a working AI-agent capability to other people without losing time, trust, or control after handoff.

**Personal B2B Job for the author.** Look competent and reliable when someone else runs my agent setup without me watching.

## 3. Pains and gains
**Pains**
- A README assumes a machine and agent harness the author has never seen.
- Native runtime install paths solve one runtime but not cross-agent handoff or governance evidence.
- Every failed install becomes a bespoke debugging thread.
- Credentials and local secrets make delegated execution risky.
- Update/repair/uninstall is often not documented, so first install support repeats later.
- Security reviewers ask "what will this change?" and the author has no compact evidence artifact.

**Gains**
- The setup becomes a package of work, not a pile of prose.
- The recipient's own agent runs the work locally, so secrets stay local.
- The plan is previewed before change.
- Verification and receipts prove what happened.
- Repair/update/uninstall use prior state instead of rediscovering it.
- The same artifact can later feed a private catalog or BYO-agent execution lane.

## 4. Before -> After
| | Current Job Graph | WPM Job Graph |
|---|---|---|
| Core Jobs performed | Author explains setup; recipient interprets docs; both debug differences; author re-supports updates | Author packages setup; recipient's agent previews, runs, verifies, records, and can re-enter lifecycle |
| What the author still does | Writes docs, answers support, reconstructs environment, explains risk, repeats fixes | Defines bundles, checks, approvals, and receipt expectations once |
| What the recipient still does | Reads docs, chooses steps, copies config, guesses what broke, asks author | Approves plan, provides local permissions/secrets when needed, reviews result |
| Dominant-criteria outcome | Completion depends on recipient skill and environment match | Completion probability is raised by preflight, task graph, verification, receipts, and repair path |
| Local control | Often implicit or violated by support/delegation | Explicit: local agent/auth, plan preview, no secret handoff by default |

## 5. Our value - benefit themes
1. **Fewer failed handoffs.** WPM repairs the setup chain before the recipient starts: dependencies, target agents, preflight, verification, and plan preview are part of the package.
2. **Less author support.** The repeated support thread becomes a reusable task graph with acceptance criteria and receipts.
3. **More trust before execution.** The recipient sees what will change, keeps secrets local, and gets evidence afterward.
4. **Lifecycle instead of one-shot install.** Update, repair, and uninstall are not afterthoughts; they read the same receipt.
5. **A bridge to enterprise later.** Manifests, hashes, target agents, permissions, and receipt summaries can become a governance evidence dossier without making WPM a full control plane.

## 6. Differentiation vs competitive alternatives
| Dominant success criterion | README/scripts | Hermes native distribution | MCP/skill registry | Governance/scanner products | WPM |
|---|---|---|---|---|---|
| Install completes in unknown environments | Weak: prose depends on recipient interpretation | Strong inside Hermes, weaker cross-runtime | Weak: distributes components, not setup work | Not the install unit | Strong if work package is authored well |
| Author support thread shrinks | Weak | Medium inside one runtime | Weak-medium | Indirect | Strong: task graph + verification + receipt |
| Recipient keeps local control | Medium: local, but opaque | Strong for Hermes profile data | Medium: depends on component | Strong for policy, not execution | Strong: local agent/auth + approval + receipt |
| Lifecycle is re-enterable | Weak | Medium-strong inside Hermes | Medium for component update | Not installer lifecycle | Strong if receipt loop works |
| Cross-agent handoff | Weak | Weak: Hermes-specific | Medium: protocol/component-specific | Strong visibility, weak package execution | Strong target-agent surface hypothesis |

**The wedge:** WPM owns the intersection of **portable setup work + local execution + verification receipt**. Component marketplaces answer "what can my agent load?" Governance tools answer "what agents/assets exist and are allowed?" Native runtime distribution answers "how do I share this runtime's profile?" WPM answers "how do I make this setup true in someone else's environment, and prove it?"

## 7. Proof and the Aha Moment
**Aha Moment:** the author watches a recipient's own agent install a real package on a machine the author cannot inspect, verify success, and produce a receipt + how-to-use close without a support call.

Place it earlier by making the first reference package public and easy to run: the author should see a recording/transcript of the same package succeeding in a foreign environment before investing in authoring their own.

Proof needed:
- A/B against native Hermes distribution docs and a README path.
- 5 external installs, not team-controlled machines.
- Receipt enables at least one resume, repair, update, or uninstall event.
- At least 2 external authors ask to package their own setup after seeing the run.

<a id="l3-bet"></a>
## 8. Value hypothesis
**We believe that cross-runtime setup authors performing repeated agent setup handoffs will adopt WPM when a WPM-wrapped reference package completes unfamiliar-environment installs with lower author support than native docs/README, because WPM removes the support cycle and raises trust through local execution, plan preview, verification, and receipts.**

Primary value proposition:

> For cross-runtime setup authors, WPM packages a working agent setup into verified local work that another person's agent can run without handing over secrets or starting a support thread.

Supplementary value proposition:

> For internal AI/platform enablement teams, WPM emits package evidence dossiers that make approved agent setup work reviewable before a private registry exists.

## 9. Success metric and threshold
**Metric:** author support minutes per successful recipient install, compared against native docs/README.

**Confirm at:** 5 external installs, at least 4 successful without author remote-control debugging, median author support under 15 minutes, and at least 3 recipients say plan preview/receipt increased willingness to run it.

**Kill below:** fewer than 3 successful installs, or no meaningful support-time reduction versus native docs/README, or recipients reject local agent execution despite preview/receipt.

## 10. The 3 bets most likely to kill this - and the cheapest tests

### Risky assumption #1: Repeated handoff pain is real and expensive enough
**Bet:** At least 6 of 12 target authors have shipped similar agent/profile/MCP/toolchain setups 3+ times and can show a recent failed install or support thread.
**Risk if wrong:** WPM solves an elegant but low-frequency problem; build spend produces a category artifact without urgent buyers.
**Probability x cost:** High x ~$100k-$300k - this is the root Segment+Jobs risk and everything downstream depends on it.
**Validate by:** 12 author interviews using past handoff artifacts, support threads, and repos (1 week). Confirms: 6+ show repeated pain and ask to try packaging. Kills: fewer than 4 have repeated pain or support evidence.

### Risky assumption #2: WPM beats native docs/README on a real install
**Bet:** A WPM-wrapped Hermes/profile package completes unfamiliar-environment installs with less author support than native Hermes distribution docs or a README.
**Risk if wrong:** WPM adds ceremony on top of a native path that is already good enough.
**Probability x cost:** High x ~$50k-$150k - a failed reference package kills the near-term wedge but cheaply.
**Validate by:** A/B 5 WPM installs vs 5 native/README installs across unfamiliar machines/agents (2 weeks). Confirms: WPM wins on completion/support/receipt trust. Kills: native/README performs similarly or better.

### Risky assumption #3: External authors can author packages without WPM team hand-holding
**Bet:** 5-10 external authors can create a first useful WPM package from templates and the authoring skill with less than 2 hours of WPM-team assistance each.
**Risk if wrong:** WPM becomes a services business or expert-only format; registry/store supply cannot scale.
**Probability x cost:** Medium-high x ~$100k-$250k - it threatens supply, unit economics, and channel.
**Validate by:** Observed authoring sessions with one template and no bespoke coaching (2 weeks). Confirms: 5 authors publish runnable packages; kills: most require team intervention or misunderstand the package model.

## 12. Methodology appendix

Mechanics applied:

| Job node | Mechanic | How WPM applies it |
|---|---|---|
| Author explains setup repeatedly | Kill cycles | Replaces recurring support loop with reusable install-backlog tasks |
| Recipient interprets docs | Take part of the Job off the customer | Recipient's agent reads and executes structured work |
| Recipient fears opaque local changes | Remove negative emotions | Plan preview, confirmation levels, local secret handling, receipt |
| Unknown environment breaks setup | Fix Critical Chain breaks | Preflight/detect/setup/verify tasks before claiming success |
| Author must support update/repair | Perform more Jobs with one Solution | Same package handles install, repair, update, uninstall |
| Security/platform asks what will change | Perform Next Job in chain | Evidence dossier bridges toward approval/catalog |
| Native runtime handles only its profile | Better meet criteria on cross-agent control | Target-agent surfaces and portable package wrapper |
| Recipient loses context after interruption | Reduce time gaps / preserve state | Receipt and task statuses let agent resume |

Forces of behavior change:
- Added value: higher completion probability and lower support time.
- Problems surfaced: README/native docs fail when environment differs; support cycles repeat.
- Fears reduced: local plan preview, no secret handoff, receipts, reversible lifecycle.
- Habit reused: authors still package files/docs/config; recipients still use their own agent. WPM changes the structure under the handoff, not the whole habit at once.
- Competing graph fired: "just ship a README" now looks risky because it cannot prove install state or support repair/update/uninstall.
