# work-package-manager - what the research says
2026-06-24 · agent-native work packaging · current repo: working builder CLI

## The answer: promising, but aim narrower
The current product is not yet an app store, governance platform, MCP marketplace, or security scanner. It is a **builder for portable, agent-executable work packages**: a maintainer packages a backlog of install/setup work, and the recipient's own agent runs it in the recipient's environment. [why narrow ▸](#l2-verdict)

> **Validation debt:** this stands on **8** risky assumptions, **3** of them fatal. The fatal ones are: authors feel repeated handoff pain, they trust backlog-as-recipe, and packages really install across varied agent environments. [see them ▸](#l2-risks)

## Who to sell to
Sell first to **technical authors who repeatedly hand off agent/workflow setups into environments they cannot see**: AI automation studios, agent-tool maintainers, devtool authors, and internal AI enablement teams publishing repeatable setups. [how we found this buyer ▸](#l2-buyer)

## Why they would buy
They currently ship a README, a prompt, a list of skills, MCP config, scripts, and "please run these steps" support. WPM turns that into a package with a manifest, bundles, dependency checks, install-backlog tasks, verification criteria, receipts, repair/update/uninstall semantics, and cross-agent surfaces. [the edge ▸](#l2-edge)

## The one thing that decides everything
Can a real recipient's agent install a non-trivial package in a messy machine better than a README/script/human support call? If not, the differentiation collapses into "another agent project template." [risk list ▸](#l2-risks)

## Do this next
Run 5 concierge installs with one concrete package, preferably a Hermes profile / MCP+skills setup / project toolchain handoff, on machines the author has never seen. Measure whether WPM reduces support time and failed handoffs. [action plan ▸](#l2-next)

## How big
The broad future category could plausibly support **~$100M-$800M/yr** globally if it becomes builder + private registry + governance metadata. The current builder wedge is much smaller, likely **~$3M-$60M/yr** until distribution exists. Size is not the near-term constraint; proof of repeated author pain is. [sizing ▸](#l3-sizing)

## Why "narrow", not a clean yes

The repo has a real product spine: TypeScript CLI, templates, authoring skill, Backlog.md integration, build dry-run/package, dependency validation, lockfile integrity service, front-door transforms, and a large test suite. In a fresh build, `wpm init` produced an authoring workspace with `wip/`, `project targets add` and `bundle new` updated the deliverable, `project validate` passed, `build dry-run` listed 30 shippable paths, and `build package --format tarball` wrote a distributable archive under `builds/`. The test suite passed: 96 files, 1217 tests.

But the market ambition is broader than the product. There is no registry, no hosted execution, no outcome fulfillment, no security policy engine, and no scan/governance control plane. So the right verdict is: **NARROW** to the builder wedge now, then expand only after proof that authors repeatedly need this package format. [full chain ▸](#l3-verdict)

## The buyer, in a bit more detail

The strongest first buyer is an author who has already done the same setup several times for other people and is tired of support drag: "install these skills, wire this MCP server, place these files, run these checks, keep your own secrets." They care less about a beautiful marketplace and more about whether the recipient's agent can run the work, verify it, resume it, repair drift, and uninstall safely.

Other good-but-later buyers:
- **Internal AI platform teams**: high willingness to pay, but procurement/security cycles slow down learning.
- **Hermes/profile/runtime maintainers**: strong adjacent fit, but their first instinct is runtime-native distribution.
- **Security/governance owners**: real budget, but WPM currently supplies auditable package structure, not the control plane they buy.
- **Skill/MCP marketplace owners**: mostly partners/channels, because their unit is a skill/server/plugin, not a stateful install procedure. [full segment map ▸](#l3-segments)

<a id="l2-edge"></a>
## The edge, in plain terms

Existing marketplaces answer "what capability can my agent load?" Existing scanners answer "is this installed component risky?" Existing governance tools answer "which agents exist and who controls them?" WPM answers a different question: **"Can I package a concrete unit of work so someone else's agent can make it true in their environment, prove it, remember it, repair it, and remove it?"** [matrix ▸](#l3-differentiation)

### S1 - Repeat handoff authors ✅

> Focus here first. They are the people for whom WPM's current product performs the most complete job.

#### Persona
An AI automation studio, agent-tool maintainer, or devtool author has a setup that works locally, but every customer install becomes a support thread. They need to package skills, MCP config, files, scripts, checks, and instructions so the recipient's own agent can execute them without the author seeing the target machine.

#### Core Jobs
1. **When** I have a working agent/tool setup and must give it to someone whose environment I cannot inspect, **I want to** package the setup into a repeatable unit with observable checks, **with success criteria** the recipient's agent can install it, pause safely, verify it, and report what changed, **in order to** reduce failed handoffs and support load.
2. **When** I need to ship a new version of that setup, **I want to** update the recipe without losing the recipient's local decisions and secrets, **with success criteria** the old state is detected, migrations run only when needed, and drift can be repaired, **in order to** keep the capability working after release.

#### Why this segment, scored
| Factor | Rating | One line |
|---|---|---|
| Added value | strong | WPM replaces README/script/support handoff with recipe, receipt, verification, and package build |
| Demand we can generate | strong | Authors are reachable in agent-skill, MCP, devtool, and automation communities |
| Target margin per unit | medium | OSS CLI limits direct price; private registry/support can monetize |
| Size × switchability | medium | Narrow today, but triggered users are highly switchable |
| Existential-risk gate | pass | Hard execution, but no legal impossibility |

**Compose to focus?** Yes. This is the current product's natural first market.

### S2 - Internal AI enablement teams ⚠️

These teams need repeatable, auditable rollout of agent setups across repositories, departments, and target agents. The value gap is strong, but the current repo lacks org-level policy, private registry, approval workflow, and central visibility.

Core Job: **When** teams are creating agent setups in inconsistent ways, **I want to** standardize how setups are packaged, verified, and updated, **with success criteria** teams can reuse packages without losing auditability or control, **in order to** scale internal agent enablement safely.

Selection screen: added value strong, demand medium, margin strong, size×switchability medium, risk pass. Hold until 3-5 author-side wins exist.

### S3 - Runtime/profile ecosystem maintainers ⚠️

Hermes is the clearest signal. Hermes profiles are separate home directories with config, env, SOUL.md, memories, sessions, skills, cron jobs, and state database. Hermes profile distributions package a complete Hermes agent as a git repo with personality, skills, cron jobs, MCP connections, and config. That overlaps with WPM's "package a capability setup" ambition.

WPM can win only if it becomes the neutral adapter above runtime-native profiles: it packages profile distributions, skills, MCP connections, and install/verify/update tasks across target agents. It should not fight Hermes inside Hermes.

Selection screen: added value medium, demand medium, margin medium, size×switchability medium, risk pass. Best as template/adapter expansion.

### S4 - Security/governance owners ⚠️ partner

They buy inventory, policy, ownership, least privilege, monitoring, and approval. Microsoft Agent 365 positions itself as a control plane to observe, govern, and secure every agent. Snyk Agent Scan scans installed agent components. JFrog AI Catalog positions around central AI supply-chain governance. WPM currently does not perform this job.

What WPM can offer them later: package manifests, receipts, hashes, dependency graphs, confirmation levels, and evidence trails. That is valuable input to governance, not a governance product by itself.

Selection screen: added value medium, demand hard, margin strong, size×switchability strong, risk pass. Partner/integration, not first buyer.

### S5 - Skill/MCP/plugin marketplace operators ⚠️ channel

Skills, plugins, and MCP marketplaces already exist and grow quickly. Their unit is a component: skill, plugin, MCP server, app. WPM's unit is a work package that may install those components and verify environment state. They are distribution partners and future registry comparables, not the immediate enemy.

Selection screen: added value medium, demand medium, margin medium, size×switchability medium, risk pass.

### S6 - Outcome buyers / app-store shoppers ❌ not now

They want to buy a result, not author a package. The current repo does not supply hosted execution, escrow, SLA, billing, support, or result verification by the platform. Entering here now would force a different product before the package format has been proven.

## 3. Differentiation hypothesis

### Positioning
> For technical authors who repeatedly hand off agent/workflow setups, WPM is the builder for portable, agent-executable work packages: it turns a setup into bundles with install-backlog recipes, payloads, target-agent surfaces, validation, build packaging, and receipt-ready lifecycle semantics.

### What the current repo actually gives

Observed from source, CLI, sample run, backlog, and tests:
- Working Node/TypeScript CLI with `init`, `template`, `project`, `bundle`, `build`, `completion`, and `skill install`.
- Authoring workspace model: root `AGENTS.md` for the authoring agent, hidden `.authoring-backlog`, `wip/` deliverable, and `builds/` output.
- Bundle model: `bundle.yml`, default three-task install-backlog, payload dirs, installer-skills, advisor skill.
- Target-agent adaptation: scope aliases and build-created front-door aliases such as `CLAUDE.md`.
- Build behavior: dry-run enumerates shippable tree; package outputs an un-nested archive; `_AGENTS.md` is transformed to canonical `AGENTS.md` and aliases.
- Validation: targets, orphan bundle dirs, dependency constraints, cycles.
- Integrity substrate: `wpm.lock` format and vendored artifact hashing.
- Bundled `installer-builder` Agent Skill that teaches an authoring agent how to drive the CLI.
- Quality proof: `npm test` passed 96 test files / 1217 tests.

Current limits:
- No public registry, discovery, ratings, billing, hosted install, or app store.
- No security scanner or policy engine.
- No org inventory/control plane.
- Only minimal/default templates are visible in repo; richer template catalog is future work.
- WPM does not execute installs itself; execution is always the recipient's agent.

### Underserved wedge

The underserved intersection is **portable setup work + observable verification + persistent receipt**. Skill marketplaces do the "portable component" part. Governance products do "policy and risk" part. Hermes profile distributions do "whole profile" inside one runtime. WPM's wedge is that the thing being packaged is not a skill, server, app, or profile alone - it is the work that makes a capability true in a target environment.

### Value-creation direction

Mechanic direction: **take work off the author and recipient**. The author stops writing fragile handoff instructions; the recipient stops assembling steps manually; the agent gets a structured recipe and receipt.

## 4. Strategic recommendation and pivot options

### Verdict

**NARROW.** The chain holds for S1:

Market → agent ecosystems are growing and fragmented.
Segment+Jobs → repeat handoff authors are visible and reachable.
Value → WPM gives a stronger lifecycle than README/skills-only packages.
Unit economics → direct CLI monetization is weak, but private registry/support/services can work.
Channels → agent communities, devtools, Hermes/MCP/skills ecosystems.

The chain does **not** yet hold for broad app store, governance platform, or outcome marketplace.

### Direction "вширь": package agents/profiles

Good direction, but treat it as **payload/template expansion**, not a new store yet.

Concrete move: build a `profile-distribution` template that packages a Hermes profile distribution as a WPM bundle:
- detect Hermes/profile state,
- install/adopt distribution,
- preserve API keys/memories/sessions,
- verify profile boots and required MCP/skills are available,
- record receipt and inverse operations.

This lets WPM ride the Hermes trend without pretending to replace Hermes native profiles.

### Action plan

1. **Build one reference package** around a painful, concrete setup: Hermes profile distribution, MCP+skills stack, or project toolchain.
2. **Run 5 live installs** where the package author cannot inspect the machine beforehand.
3. **Measure support avoided**: time to install, manual interventions, failed tasks, user trust pauses, and successful resume/repair.
4. **Interview 12 repeat authors** and require evidence of past repeated support pain.
5. **Choose the next layer** only after the data: profile templates, private registry, governance export, or managed execution.

### Detailed validation plan

**Assumption 1: repeat handoff pain is urgent**
- Method: past-behavior interviews.
- Steps: recruit authors from skills/MCP/Hermes/devtool communities; ask for the last 3 times they handed a setup to someone else; collect failure/support incidents.
- Kill criterion: fewer than 6 of 12 have repeated support incidents or a current workaround.
- Cost/time: 1-2 weeks.

**Assumption 2: WPM beats README/script handoff**
- Method: concierge A/B install.
- Steps: same capability as README/script and WPM package; 5 recipients use each; author does not inspect the environment.
- Kill criterion: WPM does not reduce failed installs or support time by at least 30%.
- Cost/time: 1-2 weeks after reference package.

**Assumption 3: receipt lifecycle matters**
- Method: update/repair simulation.
- Steps: install v0.1, modify local state, ship v0.2 migration, run repair/update; record if task receipt helps.
- Kill criterion: authors/users do not value resume/repair/uninstall enough to tolerate added structure.
- Cost/time: 3-5 days.

**Assumption 4: governance is secondary**
- Method: buyer preview.
- Steps: show manifest, lockfile, receipt, and install plan evidence to security/platform owners; ask what is missing to approve a package.
- Kill criterion: security teams require a scanner/policy engine before they would approve any WPM package.
- Cost/time: 1 week.
