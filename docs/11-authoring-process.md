# 11 · The Authoring Process

Where `09` describes the install-backlog being walked at *runtime* by the executing agent, this describes the **authoring-backlog** being walked at *design time* by the authoring agent. Same substrate (Backlog.md); different walker; different task vocabulary; different lifecycle. The doc set has spent its energy on what ships and what runs; this is the meta-tooling layer — our project's zone of responsibility, distinct from the user's installer-project we're helping create.

Read with `04` (the authoring agent's behavioural protocol — the rules), `10` (the CLI surface that protocol dispatches through), and `09` (the runtime counterpart this doc parallels).

## 1 — Where the authoring work lives

Each installer-project the author builds is generated inside an **authoring workspace** that wraps the deliverable (`06`). The authoring backlog lives at the **workspace root** alongside the authoring front door — hidden, so it doesn't pollute the deliverable — while the bundle-project the author is building sits one level down in the deliverable subdirectory `wip/`, and build output is isolated in `builds/`:

```
<authoring-workspace-root>/               ← the AUTHORING surface (never shipped)
├── AGENTS.md                             ← authoring front door: flips an agent into "author this bundle-project" mode (04, 12)
├── .authoring-backlog/                   ← OUR zone: the agent's work tracker (gitignored, builder-time only)
│   ├── config.yml                          task_prefix=authoring
│   └── tasks/
├── wip/                                  ← the DELIVERABLE being authored = the shipped artifact (06/07)
│   ├── manifest.yml                          the shipped project's index
│   └── bundles/
│       └── <bundle-id>/install-backlog/      runtime recipe (ships to users)
└── builds/                               ← build output: the archives `wpm build` emits (isolated)
```

Paths to **deliverable** contents named throughout this doc (`manifest.yml`, `bundles/<id>/…`, `installer-skills/`, the scope-alias symlinks, the deliverable's executor front door) are relative to the deliverable subdirectory `wip/`; paths to the **authoring backlog** are relative to the workspace root. The built archive is exactly the `wip/` deliverable un-nested to the archive root (`06`); none of the workspace wrapper — authoring front door, `.authoring-backlog/`, `builds/` — is ever part of a shipped artifact.

Three properties make the workspace root the right home for the authoring backlog:

**Hidden, gitignored by default.** It's per-author working state, not part of what the installer ships. A second author picking up the project may want to reconstruct their own backlog from current state rather than inherit a stale work-tracker. Sharing the authoring-backlog via git is an explicit decision, not the default.

**Its own Backlog.md root.** Separate from any bundle's install-backlog so its task IDs (`authoring-1`, `authoring-2`, …) never collide with recipe task IDs. The `task_prefix=authoring` setting makes the distinction visible at a glance.

**Materialised incrementally by CLI commands.** Tasks aren't generated by a periodic scan-and-refresh; they're created the moment a CLI command introduces new authoring scope. `wpm init` populates the backlog with the project-wide planning, meta, release, and review tasks (plus a per-bundle set for each bundle the template pre-includes). `wpm bundle new` adds the per-bundle set when the author scaffolds a new bundle. `wpm bundle <id> version bump` adds the bump-specific review tasks. Other scope-changing commands (`bundle <id> requires add/remove`, `project targets add`, and the skill-adding commands when they scaffold a stub) materialise their own focused follow-up tasks. There is no `wpm plan` or equivalent — task creation is tied to project mutation, not to a re-scan step.

## 2 — Authoring tasks are plain Backlog.md tasks

An authoring task is nothing more than an ordinary Backlog.md task: a **title**, an **acceptance criterion** (free text the agent self-attests against — not auto-evaluated), and a **status**. No milestones, no phase labels, no bundle labels, no idempotency keys. The title carries whatever distinguishing information a task needs ("Plan bundle web-handoff", "Review state-tasks for web-handoff at 0.2.0"), and that's enough — the agent reads titles, picks work, and marks tasks Done.

Idempotency, where it matters, is by title: when a command would materialise a task, it first checks whether a task with that title already exists in `.authoring-backlog/` and skips if so. That's the entire mechanism — no dedicated metadata to maintain.

## 3 — How tasks are materialised

Every authoring task is created by **some specific CLI command running at some specific moment** — the moment that command introduces new authoring scope into the project. The CLI's role is structural (mutate `manifest.yml` / `bundle.yml` / disk) plus task-materialising (create the follow-up authoring tasks). The agent's role is to work through those tasks via Backlog.md and the rest of the CLI.

Each task is created by some command, with a title that's stable across re-invocations; a command checks for an existing task of the same title before creating, so re-running never duplicates. The full catalog, organised by originating command, follows. ACs are free-text criteria the agent self-attests against (no CLI auto-close); a task moves to Done because the agent did the work and set it Done, not because the CLI re-evaluated.

### Materialised by `wpm init`

Project-wide tasks the project has at minimum:

- **"Set project metadata"** — AC: `manifest.yml.project` has `description`, `license` (and ideally `repository`, `author`) set via `wpm project meta`. Agent satisfies by running the meta command with the right flags.
- **"Confirm target agents"** — AC: `manifest.yml.targets` has at least one entry. Agent satisfies via `wpm project targets add`.
- **"Verify manifest coherence"** — AC: `wpm project validate` exits clean (deps resolve, targets non-empty, valid semver, no orphan bundle dirs).
- **"Verify scope-alias symlinks"** — AC: each scope-alias under the deliverable subdirectory `wip/` corresponds to a target agent in `manifest.yml.targets` and points at `installer-skills/`; no bare `skills/` aliases exist (the safety guard against scope-name confusion from `05`). Catches drift where the author manually created or deleted an alias.
- **"Verify the executor front door reflects current bundles and targets"** — AC: the deliverable's author-owned executor front door (`wip/_AGENTS.md`, and each bundle's `wip/bundles/<id>/_AGENTS.md`) reflects the current `manifest.yml` targets and enabled bundles, and the main installer skill `<project>-installer/SKILL.md` reflects the current `manifest.yml` + each enabled `bundle.yml`. The executor front door is **author-owned, not auto-regenerated** — it is edited under the reserved `_AGENTS.md` prefix and the build strips that prefix to the live `AGENTS.md` (`10`, `12`) — so this task is where its drift against the current targets and entry points is caught (the agent spot-checks it names the current target agents and the current install shape). The main installer skill, by contrast, *is* re-rendered on every mutating CLI command, so for it this task primarily catches sidestepping (manual edits to `manifest.yml` or `bundle.yml` that bypassed the CLI). Agent confirms by mtime comparison (for the derived skill) and by spot-checking the author-owned front door against the manifest.
- **"Verify helpers and advisors registered"** — AC: every SKILL.md under `installer-skills/` at root scope corresponds to a registered helper or advisor (catches drift in either direction).
- **"Bump project release version"** — AC: `manifest.yml.project.version` has been advanced since the previous release tag (or set explicitly for the first release).
- **"Build dry-run"** — AC: `wpm build dry-run` exits clean.

If the project template used by `init` pre-includes bundles in `manifest.yml.bundles`, `init` also materialises the **per-bundle task set** (below) for each of them — the same set `bundle new` would materialise for a freshly-created bundle.

### Materialised by `wpm bundle new <id>` (and `bundle enable <id>`, idempotently)

The per-bundle authoring task set, scoped by the `bundle:<id>` label:

- **"Plan bundle `<id>`"** — AC: `bundles/<id>/bundle.yml` has `summary`, `version`, `confirmation-level` set; the `requires` map declares any inter-bundle dependencies.
- **"Fill install-backlog for `<id>`"** — AC: at least one `kind:state` task with a `step:<slug>` label exists; DoD is configured in `install-backlog/config.yml`; the detect/setup/verify trio is present. Agent satisfies via `cd bundles/<id> && backlog task create …` directly, applying the V2 tagging conventions from `08`.
- **"Author payload for `<id>`"** — AC: `payload/files/` and `payload/templates/` are populated for whatever the install-backlog tasks reference via `--ref`.
- **"Scaffold payload skill for `<id>`"** — AC: if the bundle delivers a runtime agent skill, at least one is registered via `bundle <id> skills add <name>` (which scaffolds a stub + its own per-skill "Write payload skill" task, or attaches an existing one); if the bundle delivers no runtime skill, the agent closes this with a note to that effect. This is the *decide-and-kick-off* task; the per-skill content tasks are materialised by `skills add` itself.
- **"Write advisor content for `<id>`"** — AC: `installer-skills/<id>-advisor/SKILL.md` has a real trigger description (firing on the user's *need*, per `05`) and a recommendation body, replacing the template-rendered placeholder. Materialised alongside the auto-rendered advisor stub; **not** materialised when the bundle was created with `--no-advisor`.
- **"Verify step slug uniqueness for `<id>`"** — AC: every `step:<slug>` label across `bundles/<id>/install-backlog/tasks/` and `archive/` is unique; no archived task's slug collides with an active one (the post-recycle hazard from `08`).
- **"Verify DoD compliance for `<id>`"** — AC: every task in the bundle carries the DoD items declared in `bundles/<id>/install-backlog/config.yml.dod`.
- **"Verify payload references for `<id>`"** — AC: every `--ref <path>` value in the bundle's tasks corresponds to a file registered under `bundle <id> files` or `bundle <id> templates`.
- **"Verify skill registration for `<id>`"** — AC: every payload skill registered via `bundle <id> skills add` and every install-time skill registered via `bundle <id> installer-skills add` has its SKILL.md present at the expected path with valid frontmatter; the advisor (unless opted out) has been filled past its placeholder.
- **"Verify version constraints for `<id>`"** — AC: every entry in `bundles/<id>/bundle.yml.requires` resolves against the depended-upon bundle's declared `version`.
- **"Review install-backlog independence for `<id>`"** — AC: no hard-coded IDs from other bundles appear in this bundle's tasks; no undeclared host-environment assumptions. Agent self-reviews and records findings; closes on explicit "no issues found" note.
- **"Simulate fresh-install executor for `<id>`"** — AC: agent walks `bundles/<id>/install-backlog/tasks/` as a context-less executor would, in dependency order, documenting any task whose AC would be ambiguous, whose `--ref` would resolve to nothing, or whose preconditions aren't established by earlier tasks. Closes on a clean walk.

### Materialised by `wpm bundle <id> version bump`

- **"Review state-tasks for `<id>` at `<new-version>`"** — AC: state tasks edited in this release have their milestone advanced to `<new-version>`.
- **"Consider migration tasks for `<id>` `<prev>→<new>`"** — AC: any state task whose AC changed in this release has either had its milestone bumped or had a corresponding `kind:migration` authored.
- **"Simulate upgrade for `<id>` from `<prev>` to `<new>`"** — AC: agent walks the upgrade path, verifies from-version gates fire correctly on migration tasks, verifies state-task edits don't break the upgrade. Closes on a clean walk.
- **For each bundle whose `requires` map names `<id>`: "Review version constraint on `<id>` at `<new-version>`"** — AC: `<requirer>`'s `bundle.yml.requires.<id>` constraint still satisfies `<new-version>`; if not, either the constraint is widened or a migration is authored in `<requirer>` to match the new contract.

### Materialised by `wpm bundle <id> requires add/remove`

- **Add**: "Adapt `<id>`'s install-backlog and payload to use `<dep>`" — AC: the bundle's tasks actually reference and use the new dependency (rather than the requires entry being aspirational).
- **Remove**: "Verify `<id>` no longer references `<dep>`" — AC: no install-backlog task in `<id>` references `<dep>`'s services; payload doesn't assume `<dep>` is installed.

### Materialised by `wpm project targets add <agent>`

- **Per bundle**: "Verify `<id>`'s install-backlog works on `<agent>`" — AC: install-backlog tasks don't make hard-coded other-agent assumptions; the bundle's flow is compatible with `<agent>`'s capabilities.

### Materialised by the skill-adding commands (scaffold branch only)

When `bundle <id> skills add`, `bundle <id> installer-skills add`, or `project installer-skills add` is invoked for a skill that doesn't exist yet, the command renders a stub and materialises the matching content task. (When the skill already exists, the command attaches it and materialises nothing.) `bundle <id> advisor add` and `bundle new`'s auto-advisor are the same pattern.

- **"Write payload skill `<name>` for `<id>`"** — AC: the stub's placeholder runtime-trigger description and body are replaced with real content (triggers on the bundle's runtime use, per `05`).
- **"Write content for install-time skill `<name>`"** — AC: the stub's placeholder is replaced with a real description and body. (For a bundle-scoped skill the title names the bundle too, e.g. "Write content for install-time skill detect-os in web-handoff".)
- **"Write advisor content for `<id>`"** — as above; materialised by `bundle <id> advisor add` (and by `bundle new` unless `--no-advisor`).

## 4 — The lifecycle: command-driven materialisation, agent-driven completion

A text-schema view, parallel to `09`'s loop:

```
   CLI COMMAND THAT INTRODUCES SCOPE
   (init, bundle new, bundle <id> version bump, requires add/remove,
    project targets add, skill-adding commands, bundle enable)
        │
        ▼
   [MUTATE]      structural mutation: manifest.yml / bundle.yml / disk
        │
        ▼
   [MATERIALISE] for each task in the command's catalog:
                   if a task with that title already exists in .authoring-backlog/: skip
                   otherwise: backlog task create "<title>" --ac "<criterion>"
        │
        ▼
   ┌──────────────── AGENT WORK LOOP ──────────────────────┐
   │                                                        │
   │  list outstanding work:                                │
   │      cd .authoring-backlog && backlog task list \      │
   │          --plain -s "To Do"                            │
   │                                                        │
   │  pick a task (titles read in a natural order:          │
   │      plan → fill → payload → review → release,         │
   │      but nothing enforces it)                          │
   │  set status: In Progress                               │
   │  do the work via the rest of the CLI (10) +            │
   │      Backlog.md directly in the relevant bundle        │
   │  self-attest completion: set status Done               │
   │                                                        │
   │  …back to listing                                      │
   └────────────────────────────────────────────────────────┘
        │
        ▼
   AUTHORING DONE when:  cd .authoring-backlog && backlog task list -s "To Do" --plain  ──▶ empty
```

There is no periodic re-plan. The backlog stays current because **every command that changes project scope materialises the matching follow-up tasks at the moment of the change**. The agent never has to ask "is the backlog up to date?" — it is, by construction, as long as project state was changed through the CLI.

Sidestepping the CLI is the one way the backlog can fall behind reality (e.g., the author edits `manifest.yml` directly to add a bundle without running `bundle new`). The honest cure is: don't do that. The CLI is the authority on project mutation, and the backlog stays in sync only as long as you use it.

## 5 — Composition with `04` and `10`

Three layers, each with one job:

| Layer | Job | Doc |
|---|---|---|
| **Behavioural protocol** | What the agent *does* — draws out the author's intent, decomposes it, forces the three author decisions, simulates the executor | `04` |
| **CLI surface** | What the agent *invokes* — the commands that mutate the project AND materialise the follow-up authoring tasks at the same moment | `10` |
| **Work tracker** | What the agent *remembers* — the outstanding tasks, the done ones, where it left off across sessions | this doc |

The behavioural protocol sits *above* the work tracker (it explains *why* the agent picks particular tasks and how to do them well), and the CLI surface sits *below* it (it's how each task gets done — and is also where new tasks come from). The authoring-backlog is the spine that holds the three together over time, so the agent can hand off to a future session — or to a second author — without losing context.

The no-mirror principle from `10` applies fully here: the authoring-backlog uses **Backlog.md directly** for every read and write operation (list, view, edit, archive, search). The CLI's only contribution to the authoring-backlog is *creating tasks at the moments structural mutation happens elsewhere*; there is no `wpm plan`, no `wpm task`, no wrapper around Backlog.md's own surface.

## A worked authoring session

Putting it together end-to-end:

```
# Author kicks off the project. single-bundle ships `core`; init materialises the
# project-wide task set (8) + core's per-bundle set. core is dependency-only, created
# with --no-advisor by the template, so its set is 11 — total 19 tasks.
wpm init hermes-handoff --template single-bundle
cd hermes-handoff

# See what's outstanding, and read titles (the agent picks work by title, not by id).
# The authoring-backlog has task_prefix=authoring, so its ids are authoring-N:
(cd .authoring-backlog && backlog task list --plain -s "To Do")
#   AUTHORING-1  - Set project metadata
#   AUTHORING-2  - Confirm target agents
#   AUTHORING-3  - Verify manifest coherence
#   …
#   AUTHORING-9  - Plan bundle core
#   AUTHORING-10 - Fill install-backlog for core
#   …

# Pick "Set project metadata" — note its id from the listing, then drive it:
(cd .authoring-backlog && backlog task edit authoring-1 -s "In Progress")
wpm project meta --description "..." --license MIT --repository "..."
(cd .authoring-backlog && backlog task edit authoring-1 -s Done)

# Pick "Fill install-backlog for core" — task creation goes through Backlog.md directly
# inside the bundle. Labels are ONE comma-separated -l; --dep is by task id.
# The core bundle has task_prefix=core, so ITS task ids are core-N.
(cd .authoring-backlog && backlog task edit authoring-10 -s "In Progress")
(cd wip/bundles/core && \
   backlog task create "stand up handoff channel" \
     -l "kind:state,step:standup-channel" \
     -m 0.1.0 \
     --ac "channel reachable from agent scope" \
     --dod "ownership recorded")
# …more state tasks until the detect/setup/verify trio is complete…
(cd .authoring-backlog && backlog task edit authoring-10 -s Done)

# Adding a new bundle later — bundle new materialises another per-bundle set
# (12 with the auto-advisor; 11 with --no-advisor):
wpm bundle new pdf-handoff
# > Created bundle 'pdf-handoff'. Advisor scaffolded. Materialised 12 authoring tasks.

# Bumping a version — materialises bump-specific review tasks:
wpm bundle pdf-handoff version bump minor
# > pdf-handoff: 0.1.0 → 0.2.0
# > Materialised 3 authoring tasks (state-task review, migration consideration, simulate upgrade)
# > (plus 1 task per requirer if any bundle required pdf-handoff)

# ...continues until `backlog task list -s "To Do"` is empty
```

## Hard rules

The authoring-backlog is **per-author working state, not shipped**. `.authoring-backlog/` is in `.gitignore` by default; sharing it across authors is an explicit decision, and a new author cloning the project will start from an empty backlog (they re-derive their own work by walking the project state).

**Materialisation is idempotent by title.** Before creating a task, a command checks whether one with the same title already exists in `.authoring-backlog/` and skips if so. There's no dedicated key or label to maintain — the title is the identity. This is what makes `bundle enable` safe to re-run on a previously-authored-then-disabled bundle.

**The agent self-attests completion. The CLI never auto-closes.** A task moves to Done because the agent did the work and set Done via Backlog.md. The CLI doesn't re-evaluate ACs and doesn't override agent-set status. The AC is a free-text criterion the agent reads, satisfies, and attests against — not a machine-checked predicate.

The authoring-backlog uses **Backlog.md directly**. There are no `wpm task ...` or `wpm plan ...` wrappers — the CLI contributes to the authoring-backlog only by *materialising tasks when scope changes elsewhere*, never by wrapping Backlog.md's read/edit/archive surface.
