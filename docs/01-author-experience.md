# 01 · The Author

First of the three roles. The author isn't writing software — they're writing a runbook that has to survive environments they will never see. Everything hard about the authoring experience comes from that one fact, and the design exists to compensate for it.

The division of labor is fixed: the author brings domain truth — *what actually has to happen to set up Chromium for handoff* — and the authoring agent brings structure and three disciplines the author tends to skip. The agent is a scribe and an auditor, not the source of knowledge. And as with the end user, the author works *through* that agent in conversation — there's no authoring GUI; the `wpm` CLI (`10`) is the agent's tool, not a screen the human operates. Both humans in this system act through agents; neither touches bespoke installer chrome.

## The authoring loop

How the authoring agent behaves here isn't a fixed interactive script — it's shaped by **instructions** (the builder's own front-door and skill, `12`), so it can be tuned per project rather than hardcoded. What those instructions aim it at is a rhythm that mirrors Backlog.md's own "describe → decompose → review," applied to setup recipes rather than feature work: draw out what the author knows, shape it into bundles, and check the result with them.

The author states the piece of functionality they want to package as a bundle, and the agent — guided by its instructions, not a fixed questionnaire — draws out the unknowns the author wouldn't volunteer: what the prerequisites are, what differs across machines, how we'll *know* it worked, and where a human will have to step in. From that it drafts the bundle as three movements — detection, setup, verification — and the author reviews at a checkpoint before anything is considered done. If the draft is wrong, the author refines the description and acceptance criteria and the agent redrafts. The review checkpoint is load-bearing; it's where the author's tacit knowledge gets pulled into the explicit contract. How probing or terse the agent is, and what it foregrounds, is itself a function of the instructions — so a project can dial the experience without changing the tool.

## Three decisions only the author can make

**The trust gradient, per step.** Pin this as an authoritative reference — a fixed config file, a fixed version — or describe the intent and let the executing agent adapt? This is the single biggest lever on whether a bundle is brittle or robust, so the agent should surface it as an explicit question at the moment it's drafting each step, never leave it implicit. It's the same split Debian policy draws between shipping a best-effort file and generating one per-machine. "Spec where it's cheap, fix where it's load-bearing" is the author's recurring judgment call — bearing in mind that a pinned file is the author's *reference*, not a runtime guarantee: the executor checksums what it actually places, so divergence is detected rather than assumed away.

**Verification as the organizing principle.** Every bundle has to end by answering "how will the *end user's* agent know this succeeded?" If the author can't answer, the bundle isn't finished — verification isn't an appendix, it's the spine. This is the same proof that later becomes the basis for Repair, so writing it well pays twice.

**Confirmation level, per step.** The author knows which steps are dangerous and which are routine; they tag each accordingly. This is the UAC decision moved to authoring time, and it's the mechanism that lets a single execution serve both the cautious user and the hands-off one without the author having to guess which they're dealing with.

## What good authoring produces beyond the happy path

A bundle that only handles success is half-built. But the inverse isn't something the author hand-writes step by step: the executing agent **journals each step's inverse op as it runs**, and uninstall replays that record, so the author writes explicit reverse logic only for the genuinely complex cases (an optional reverse backlog). What the author does own is the **how-to-use close**, the bundle's equivalent of a postinstall message, so the user ends with "here's what you now have and how to trigger it" rather than a silent "done." And rather than designing a lockfile, the author sets the bundle's **Definition of Done** — the checklist that forces the executor to record the receipt (inverse op, ownership, checksum, decisions) before any step counts as finished, so a re-run reuses those decisions instead of re-deciding them. Because bundles are isolated, each carries its **own version** and can evolve without disturbing its neighbors. Versioning brings one recurring judgment the author owns: a change to *how* the bundle reaches its current state is just an edit to the idempotent state tasks, which reconcile on the next run, but a change that only makes sense for users coming *from* an older version — a renamed config, transformed data — is a new **migration** task. The discipline is forward-only: never rewrite a migration already shipped (the recorded ledger assumes applied migrations don't change underneath it), always add a new one. The mechanics live in `08`.

## The independence check

Couplings leak in unbidden — the author will quietly assume "by the time Chromium runs, core has obviously run." So independence is something the authoring agent actively checks: as part of its review pass it reads each bundle and flags undeclared assumptions, shared mutable state, hard-coded IDs, ordering taken for granted rather than declared in `requires`. This isn't a separate tool command — it's one of the review-phase tasks the agent works through per bundle (see `11`), self-reviewing and recording findings as it goes, resisting the convenient move of coupling two bundles to "make it work." The multi-root structure is what gives the check a crisp, checkable definition of "independent" to test against; without that structure it would be just vibes.

## Two moves worth building into the tool

Let the author **rehearse the install as the end user would experience it** — have the authoring agent role-play the whole thing from the consumer's side, conducting the install conversation back at the author as if they were the one being walked through it. It's the only honest way to feel whether the experience is actually good, and it routinely surfaces a question the author forgot to make answerable. This isn't a separate UI or a "preview screen" — there's no installer chrome anywhere in this system — it's the agent playing the end-user's agent in conversation. The review pass already simulates a context-less executor walking each bundle for *correctness* (see `11`); rehearsing the felt *experience* is a distinct, still-worth-building move.

And keep **the format dogfooding Backlog.md at every level**. The tool that creates bundles isn't a bespoke engine: it's the `wpm` CLI (`10`) working *above* a Backlog.md authoring-backlog (`11`) that tracks the author's own work — the very same Backlog.md a bundle's install-backlog uses. Building the creator on the same primitive it produces keeps the surface small and forces the format to live inside its own contract; the builder even tracks its own development in Backlog.md (`12`).
