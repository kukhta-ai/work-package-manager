# 04 · The Authoring Agent

This is the mirror of the executing agent (doc 03). Where that agent turns a finished bundle into changes on a machine, this one helps a human turn domain knowledge into a finished bundle. The two are the opposite ends of the same contract — and the best way to QA the contract turns out to be having this agent *play* the other one, which is the spine of this document.

The autonomy posture is inverted from the executor's. The executing agent is agent-led and mostly autonomous, pausing only at marked handoffs. The authoring agent is **human-led**: the author is sitting right there, the loop is continuous checkpoints, and the agent proposes and confirms rather than deciding. Its job is not to know the domain — it's to extract what the author knows and make it survive into the artifact.

In practice it works through two surfaces. **Structure** — creating the project and bundles, registering payload files and skills, declaring dependencies and target agents — goes through the `wpm` CLI (`10`). **Content** — the recipe tasks themselves (authored directly in each bundle's Backlog.md with the V2 tagging of `08`) and the sense-dependent prose the CLI only ever scaffolds (skill bodies, the advisor's recommendation, file contents) — the agent writes itself. That division is the CLI's "structure, not content" rule seen from the agent's side: the tool never writes the prose, the agent never hand-maintains the structure the tool owns. The agent's own progress is tracked in the authoring-backlog (`11`), whose tasks the CLI materialises as new scope appears; the agent works them like any other backlog.

## What the authoring agent must do

**Draw out what the author won't volunteer.** The author will describe the functionality they want and stop there. The agent's work is to elicit the rest — the prerequisites, what differs across machines, how success will be detected, where a human will have to step in, and how dangerous each step is. This isn't a fixed interview script; it's behavior the agent's instructions aim at, so how it elicits (probing or light, what it leads with) is tunable per project rather than baked in. The describe → decompose → review loop is the agent's responsibility to run, not the author's to remember.

**Decompose into the shape the executor expects.** Every bundle the agent drafts must come out in the uniform three-movement form the executing agent reads — detection, setup, verification — so that an executor with no other context can run it. This is the critical handshake: the authoring agent writes in exactly the shape doc 03's agent consumes. A bundle that's well-described but structurally a snowflake is a defect.

**Force the three author decisions.** The agent surfaces the trust-gradient question at each step ("pin this exactly, or describe the intent?"), refuses to call a bundle finished until the author has answered "how will the executor know this worked?", and prompts for a confirmation level on each step. It makes the author make these calls; it does not make them on the author's behalf.

**Review independence.** It actively hunts for leaked couplings — undeclared assumptions, shared mutable state, hard-coded IDs, ordering taken for granted instead of declared — and reports them, resisting the convenient move of coupling two bundles to "make it work," because that convenience is exactly what the multi-root structure exists to prevent. This isn't freeform agent behaviour: it's one of the review-phase tasks the authoring-backlog materialises per bundle (`11`), worked like any other.

**Produce the connective tissue.** It prompts for and drafts the parts authors skip: the how-to-use close and — importantly — the bundle's **Definition of Done**, the receipt contract. Just as the executing agent *records* the receipt as it runs, the authoring agent *defines what must be recorded*, deciding with the author which facts the executor has to journal (inverse op, ownership, checksum, the chosen version, the decisions worth pinning) so a later run reuses them instead of re-deciding. It designs the record the executor will later honor. It does *not* hand-write a teardown step by step — the executor journals inverse ops at do-time and uninstall replays them — so it drafts explicit reverse logic only for the genuinely complex cases the journal can't cover.

**Set up versioning honestly.** It establishes the bundle's stable `id` and current `version`, and when the author changes an existing bundle it helps classify the change: an edit to the idempotent state tasks (which reconcile on re-run) versus a new run-once **migration** task for anything that only applies when coming from an older version. It enforces the forward-only discipline — never rewrite a shipped migration, add a new one, gated on the from-version — since the tool won't enforce that immutability itself. The full convention is `08`; the agent's job is to keep the author on the right side of it.

## The strongest move: simulate the executor

The single highest-value thing this agent does is role-play the executing agent against the draft. "If I were the executor, with none of the context from this conversation, could I run this bundle? Where would I have to guess? Where would I get stuck at a step the author thinks is obvious?" Every place the simulation stalls is a place the authoring conversation held context that didn't make it into the artifact. This closes the loop without ever touching a real machine, and it's a better test than anything the author can do by reading their own draft, because the author can't un-know what they know. The same move extends to updates: it also simulates the executor arriving at the *previous* version and applying the new one, which is how it catches a migration whose from-version gate is wrong or a state-task edit that should have been a migration. Both simulations are materialised as concrete review-phase tasks per bundle — "Simulate fresh-install executor" and "Simulate upgrade" — in the authoring-backlog (`11`).

## What it must not do

It must not invent domain facts the author didn't supply — if it isn't sure how Chromium gets set up on a given platform, it asks or flags, it does not confabulate plausible-looking steps. It must not silently resolve the ambiguity the author should own (trust gradient, danger level). It must not over-pin to feel safe — fixing everything makes brittle bundles just as surely as fixing nothing makes fragile ones; it proposes, the author decides. And it must not let a bundle be marked done without verification, no matter how complete the setup steps look.

## The prime directive

The authoring conversation is rich with context; the bundle is all the executor inherits. So the agent's one job, under everything above, is to **make the implicit explicit** — to move everything tacit in the conversation into the contract, because nothing else survives the handoff. The executor gets the bundle and only the bundle.
