# Private delivery and candidate qualification

The repository produces a CLI and portable work packages. `package.json` remains private. No workflow publishes to npm, creates a release, uploads a public website, or requests publication credentials. Version records under `.changeset/` describe user-visible changes; they are not publication approval.

## Pull request checks

Use a short topic branch and a reviewed PR to `main`. The `CI / Required` job requires both the Linux policy job and all consumer matrix cells to succeed. A failed, cancelled, or skipped band fails this aggregate. A repository administrator must make that aggregate required in branch protection; the workflow cannot itself enforce GitHub settings. Protect quality policy and workflows with independent review.

Policy checks run once on Linux with Node 24. Analyzer provisioning requires pinned uv 0.11.9 and Go 1.27.3; uv prepares Python 3.13.13. The current OSV module requires Go 1.27 or newer, so implicit Go toolchain updates are disabled. Python dependencies are installed from the complete hash lock into a fresh owned environment with `--no-cache`; existing matching versions and unpacked caches never establish authority. Inner environment symlinks are refused. A real tiny-wheel qualification demonstrates that reprovision repairs same-version library tampering and rejects a modified source wheel. The version-2 setup receipt binds the lock, setup implementation and that qualification, then fingerprints the whole local environment, including dependency code. Changing a library while retaining its console wrapper fails the doctor. `quality:setup` provisions the pinned analyzers into repository-local ignored directories; a missing analyzer fails `quality:doctor`. Groma plugins are restored from the exact configured source, the package check and completed non-empty scan establish scanner compatibility, and a rescan must leave its committed map unchanged. Groma is an architecture navigation aid. The import graph and executable negative fixtures enforce architecture.

Consumer checks run on Linux, macOS, and Windows with Node 24 and 26. Each cell installs the lockfile, packs the clean source revision once, installs the inspected archive in a fresh prefix outside the checkout, checks installed resources and executable shims, then builds and runs the tests. This verifies the package that a consumer receives, including preservation of personal and workspace agent configuration. The declared legacy runtime range is a separate compatibility contract; do not infer validation of untested versions from this matrix.

The packed-install test keeps its consumer cache isolated while seeding only the exact native Backlog archive already fetched by `npm ci`. It exports the locked URL through supported offline `npm pack`, verifies the archive's SHA512 against the root lockfile, and adds those bytes to the disposable cache through `npm cache add`. A content-only cache may lack npm's URL-response index; in that case an absolute `WPM_TEST_BACKLOG_NATIVE_ARCHIVE` can supply the same archive, subject to the same mandatory digest check. A missing or mismatched archive fails with an actionable error. The fixture still performs the real global peer installation and checks its version and isolated prefix.

PR execution has read-only repository permissions, no secrets or persisted checkout credentials, no `pull_request_target` execution, pinned Action commits, and bounded timeouts. Untrusted PR code can run only in its unprivileged job. No PR cache is promoted into candidate preparation. Dependabot opens reviewed updates for packages and Action pins.

## Prepare an inactive candidate

Start with a clean committed checkout and run:

```sh
npm ci
npm run quality:setup
npm run candidate:prepare -- --output /tmp/wpm-candidate --notes .changeset/wpm-vnext.md
npm run candidate:verify -- --output /tmp/wpm-candidate
```

The output must be outside the source checkout. Preparation runs `quality:release` on that revision, then creates an owned Git clone at the exact captured commit for package production. The clone retains the full committed tree, including tracked build inputs marked `export-ignore`; ignored quality output, personal configuration and local build inputs are excluded. A normal locked `npm ci` creates its own dependency tree. The producer has an isolated home/configuration and a PATH without the contributor checkout; only npm's integrity-checked download cache is reused. Git and npm credentials or personal settings are not copied. The exact npm JavaScript entry point remains explicit where Windows requires it.

The unchanged package-boundary command runs in that producer, so its strict ignored-input check and clean/prepack lifecycle cannot erase the contributor's `dist/` or consume contributor-local state. Both the original checkout and producer retain revision/lock checks. Preparation creates one archive and passes those exact bytes through inspection, strict publint tarball analysis using the producer's locked tool, fresh consumer installation, and candidate persistence. Publint receives the tarball path directly and never repacks it. Producer scratch state is removed after success or failure; existing contributor state is preserved. It does not rebuild at verification. A build that depends on an ignored local file fails instead of importing that file into the producer.

For a slow connection, `package:verify-install` and `candidate:prepare` accept repeatable `--npm-cache-archive /verified/upstream.tgz` options. Every supplied ordinary archive is captured once and must match the SHA512, official registry entry, package name and version in the verifier's current source lockfile before consumer state is created. The captured bytes are copied into owned bootstrap staging and added to the new consumer cache through `npm cache add`; the ordinary fresh installation and dependency resolution remain unchanged. No personal cache or installed dependency directory is reused. The optional installation receipt records the lockfile digest and archive identities. Candidate preparation uses its clean source checkout as the lock authority and forwards the option only to fresh consumer verification; persisted-candidate verification needs no upstream archive or rebuild. `WPM_TEST_BACKLOG_NATIVE_ARCHIVE` remains a separate explicit test-fixture input and is never an implicit verifier option.

Use repeatable `--peer-archive /verified/peer.tgz` to select an explicit qualification peer. These archives pass the same ordinary-file, root-lock SHA512 and package-identity checks; each must name a declared peer and satisfy its actual packed manifest range. Duplicate or incompatible peers fail before consumer creation. npm receives the captured peer tarballs alongside the WPM tarball in the same normal global installation. The report records their observed installed versions and hashes, and candidate evidence preserves that report. The integration journey qualifies Backlog 1.45.2 this way while retaining WPM's legacy `backlog.md >=1.0.0` declaration. This establishes compatibility with the mapped peer; it does not certify every future version in that range. Without the explicit option, npm retains its ordinary automatic peer resolution.

`candidate.json` binds the exact archive SHA-256/SHA-512, source commit, package/version, inspection, installation and quality evidence, and release notes. `qualification.json` additionally binds the candidate record's SHA-256, Node/npm versions, operating system, architecture, and lockfile digest. The hashes detect substitution and correlate evidence; they are not signatures or proof that an untrusted workflow ran honestly. Trust comes from the reviewed workflow and clean controlled runner.

Reusing the same candidate directory rechecks persisted bytes, source revision, notes, lockfile and the explicit peer selection recorded in the immutable packed-install evidence. The requested peer names, versions and SHA512 values must match; the same bytes may come from a new path. Omitting or changing an explicit peer requires a fresh destination. Supplied cache-only archives are validated even on reuse, while their selection is a performance input rather than a qualification target. Fresh preparation stages the originally captured bytes so replacing an input path during the quality gate cannot change the selected peer. A mismatch stops; it never replaces approved bytes. A fresh preparation uses a new destination. A damaged or partially written destination requires diagnosis or removal by its owner; repair must not silently change an approved artifact. `candidate:verify` remains input-free and does not need the original upstream archives.

The manual `Private candidate` workflow first requires a private repository, then performs this local qualification and retains the candidate for 90 days. This keeps generated evidence inside the approved access boundary. It never publishes. A human approval must name the source commit, version and archive digest. Any later authorized publisher must consume the same verified archive without rebuild or package scripts, use a separate protected environment and OIDC authority, and stop on a channel digest mismatch. Such a publisher is deliberately absent until public coordinates, authority, provenance policy and rollback/fix-forward policy are approved.

## Evidence retention

Architecture exports remain local or access-controlled CI artifacts for 14 days (CI exports/uploads only for a private repository); exports contain source context. Candidate bundles remain private artifacts for 90 days. Retention is availability, not permission to publish. Raw analyzer logs and generated maps used only for inspection stay ignored working memory. Gitleaks scans an explicit Git-selected snapshot rather than ignored private tool caches. OSV matches against downloaded offline database bytes and records their hashes, sizes and timestamps even if downloading or matching fails; a download request time is not a claim about upstream freshness. Retain compact accepted decisions or gate receipts under `research/evolution/` according to `PROCESS-ARTIFACTS.md`; do not commit a whole candidate or exported website.

Actual GitHub branch protection, workflow execution, all host/runtime cells, OIDC publishing, and fresh native-agent sessions require their respective environments. A local static workflow check cannot certify them.

## Mandatory scanner policy

Scanner source is data. Gitleaks and OSV receive explicit configurations generated outside the scanned source. OSV receives an empty ignore policy. Gitleaks receives the pinned defaults and only the independently reviewed non-secret proof in `quality/secret-policy.json`. Source-root `.gitleaksignore` is rejected because this Gitleaks version otherwise loads it even with an explicit override. Source `.semgrepignore` files that can affect managed scan targets are rejected; inline `nosemgrep` and `gitleaks:allow` suppressions are disabled. Personal scanner environment overrides and service credentials are not inherited.

The existing BMAD assets contain forty metadata rows whose SHA256 values resemble API keys and nine public JWT headers truncated before payload and signature. The policy names finite reviewed identities and exact example paths. It recomputes every inventory digest from a confined Git-selected source file, including the deterministic installed native-skill projection, and accepts only the exact public example line. These exceptions target `generic-api-key` per rule with an AND condition for path and exact content. They never exclude a vendor directory or an entire file. Global path allowlists are deliberately avoided because the pinned Gitleaks version can prefilter a whole file despite an AND condition. Changed or unproved metadata fails closed.

Every security run qualifies its actual pinned binaries against adversarial local fixtures: new credentials of the same and a different rule at both approved paths must still be found; source allow-all config, ignore fingerprints and inline suppressions must not hide findings; an untrusted OSV ignored-vulnerability policy must not hide a known affected package, while the fixed version must be clean. The JWT fixture retains the complete actual Markdown file so native line framing is exercised. The pinned Gitleaks engine includes a preceding LF and may retain a CR from CRLF input; only those framing bytes are optional around the exact approved source line. The qualification uses a tiny curated local OSV fixture and synthetic credentials. The production scan separately uses the downloaded database and the complete npm lockfile. A passing fixture is not a claim that the production dependency graph is free of vulnerabilities.

Production and qualification use the same canonical command builders for Semgrep, Gitleaks and OSV. The OSV fixture selects its curated local database while production requests a database refresh; mandatory source-policy controls are shared. A separate hand-built qualification command cannot establish that production enables those controls.
